# MAO — COMPONENTS

Контракты компонентов (C01–C20). Формат каждого раздела: назначение,
ответственность, входы, выходы, взаимодействия, запреты, хранимые данные,
расширение. Идентификаторы и размещение соответствуют SYSTEM_OVERVIEW.md.
C17–C20 добавлены этапом 1.3 (ADR-MAO-009…014); контракт `RuntimeAdapter`
— API_CONTRACTS §2.16.

Общие правила контрактов:

- Все межкомпонентные структуры — типы из `packages/shared`.
- Каждый компонент объявляет интерфейс и поставляется с fake-реализацией
  для тестов.
- Вызовы между компонентами — синхронные запросы интерфейсов; наблюдение —
  через шину событий C06 (подписка, не вызовы).
- Ни один компонент не читает секреты и окружение напрямую; конфигурация
  передаётся при конструировании (как в существующих пакетах).

## C01. Employee Registry

- **Назначение.** Каталог конкретных сотрудников офиса (экземпляров,
  нанятых по профессиям).
- **Ответственность.** Регистрация, изменение, деактивация сотрудников;
  хранение ссылок Employee → Profession; выдача профиля сотрудника по
  `employeeId`; учёт назначенной модели по умолчанию и переопределений.
- **Входы.** Определения сотрудников (записи/файлы), команды регистрации от
  C16, начальная таблица `DEFAULT_AGENT_MODELS` при первичной инициализации.
- **Выходы.** `EmployeeProfile` (id, имя, professionId, departmentId,
  modelDefault, skillOverrides, статус, визуальный персонаж).
- **Взаимодействует с.** C02 (профессия сотрудника), C05 (подбор исполнителя),
  C07 (модель по умолчанию сотрудника), C16 (CRUD через API), C14 (аудит
  изменений).
- **Запрещено.** Запускать исполнение; выбирать модель в обход C07; хранить
  историю задач (это C14); дублировать текст профессии (только ссылка).
- **Хранит.** Записи сотрудников (SQLite, таблица `employees`; см.
  DATA_MODEL.md). Не хранит сессии и историю.
- **Расширение.** Новые сотрудники — регистрацией через API/файл; новые
  атрибуты — версионируемые поля профиля; реакции на изменения — события
  `employee_registered/updated/deactivated`.

## C02. Profession Registry

- **Назначение.** Каталог профессий — декларативных профилей компетенций.
- **Ответственность.** Загрузка определений профессий из файлов
  (`professions/<id>.md` с YAML-фронтматтером), валидация схемы, выдача
  `ProfessionProfile`, динамическая регистрация/обновление/отключение,
  поддержка набора 30–40 стартовых профессий.
- **Входы.** Файлы профессий; команды регистрации от C16.
- **Выходы.** `ProfessionProfile` (id, версия, роль, ответственность,
  базовые инструкции, departmentId, skillTags, capabilityRequirements,
  modelHints, acceptancePolicy).
- **Взаимодействует с.** C01 (экземпляры, отделы), C03 (skillTags для резолва),
  C05 (подбор профессий под задачу), C07 (modelHints), C14 (аудит).
- **Запрещено.** Содержать исполняемый код; знать о конкретных задачах;
  обращаться к Runtime; хранить состояние исполнения.
- **Хранит.** Определения профессий (файлы — источник истины; SQLite —
  индекс/кэш для запросов) и справочник отделов: 10–12 `Department`
  (DATA_MODEL §2.1) как группировка профессий; отдел — не процесс и не
  бюджетная единица, фильтр выборки и обоснование орг-структуры (этап 1.3).
- **Расширение.** Новая профессия = новый файл + регистрация; наследование
  профилей (`extends: <id>`) для семейств профессий; версии профессий.

## C03. Skill Registry

- **Назначение.** Каталог всех Skills (100–200+), включая общие.
- **Ответственность.** Обнаружение и загрузка описаний Skills
  (`skills/**/SKILL.md`), валидация метаданных, версионирование,
  регистрация/отключение, выдача дескрипторов (без тел) для индексации.
- **Входы.** Файлы Skills; команды регистрации от C16.
- **Выходы.** `SkillDescriptor` (id, версия, описание, категория, теги,
  requiredTools, compatibleProfessions, dependencies, токен-оценка тела).
- **Взаимодействует с.** C04 (источник дескрипторов), C02 (совместимость),
  C14 (аудит изменений).
- **Запрещено.** Загружать тела Skills по умолчанию; исполнять Skills;
  разрешать зависимости (это C04); обращаться к LLM.
- **Хранит.** Дескрипторы (SQLite-индекс); файлы — источник истины.
- **Расширение.** Новый Skill = каталог с `SKILL.md`; новые категории —
  значения перечисления; внешние источники Skills — через адаптер загрузки.

## C04. Skill Resolver

- **Назначение.** Выбор минимального достаточного набора Skills под конкретную
  подзадачу и профессию.
- **Ответственность.** Фильтрация по совместимости с профессией, тегам задачи
  и категории; разрешение зависимостей (топологически, с защитой от циклов);
  проверка доступности requiredTools; формирование пакета тел Skills для
  контекста с учётом бюджета токенов контекста.
- **Входы.** `SubtaskBrief` (от C05), `ProfessionProfile` (C02), дескрипторы
  (C03), бюджет контекста (от C09).
- **Выходы.** `SkillBundle` (упорядоченный список `skillId@version` + тела
  для включения в контекст + список отклонённых с причинами).
- **Взаимодействует с.** C03, C02, C09 (получатель пакета), C07 (оценка
  токенов влияет на выбор модели).
- **Запрещено.** Загружать весь каталог в контекст; выбирать модель;
  модифицировать тексты Skills; игнорировать лимит контекста.
- **Хранит.** Ничего (чистая функция над дескрипторами); статистику выбора
  передаёт событием.
- **Расширение.** Стратегии ранжирования (правила → статистика успешности →
  опционально LLM-ранжирование); кэш резолва по ключу (профессия, теги).

## C05. Task Router

- **Назначение.** Приём пользовательской задачи и построение плана исполнения.
- **Ответственность.** Анализ задачи; классификация сложности (simple/
  standard/complex); определение необходимых профессий; разбиение на
  подзадачи и граф зависимостей (DAG); выбор fast path для простых задач;
  назначение сотрудников через C01; постановка плана в C06.
- **Входы.** `UserTaskRequest` (от C16), каталоги C01/C02, история успешности
  (через C14, опционально).
- **Выходы.** `TaskPlan` (подзадачи, зависимости, назначенные employeeId,
  критерии приёмки, оценки стоимости/длительности).
- **Взаимодействует с.** C16, C01, C02, C04 (через назначение skillTags),
  C06 (исполнитель плана), C07 (предварительная оценка стоимости), C14.
- **Запрещено.** Исполнять задачи; выбирать конкретную модель исполнения
  (это C07 в момент запуска); требовать участия всех сотрудников; обращаться
  к LLM для простых задач (правила; LLM-планирование допустимо только для
  complex и только с одобрения политики бюджета).
- **Хранит.** Планы и их статусы (SQLite, `tasks`, `subtasks`).
- **Расширение.** Плагины классификации сложности; стратегии декомпозиции
  (rules → director-LLM); шаблоны типовых планов.

## C06. Orchestrator

- **Назначение.** Исполнение плана задачи: координация всех компонентов
  исполнения, состояние подзадач, retry-циклы, финальная приёмка.
- **Ответственность.** Обход DAG подзадач; делегирование готовых подзадач
  в C11; вызов цепочки C09→C10→C15 через существующий
  `AgentExecutionCoordinator`; приём результатов и артефактов (C13);
  инициация валидации (C12); повторные попытки с эскалацией модели (через
  C07); финальная приёмка (правила; для complex — Director-профиль через
  обычное исполнение); публикация всех событий в шину.
- **Входы.** `TaskPlan` (от C05), события исполнения (от C15 через
  координатор), результаты валидации (C12), отмены (от C16).
- **Выходы.** События состояния; `TaskResult` (итог, артефакты, usage,
  отчёт валидации); команды отмены в координатор.
- **Взаимодействует с.** C05, C07, C08, C09, C10, C11, C12, C13, C15 (через
  координатор), C14 (события), C16 (статусы).
- **Запрещено.** Обходить C08 при запуске исполнения; превышать лимиты
  параллельности; хранить секреты; блокировать event loop длительными
  операциями; модифицировать план без события `plan_revised`.
- **Хранит.** Состояние подзадач (SQLite); in-memory — только активные
  дескрипторы (как сейчас `running` в координаторе).
- **Расширение.** Политики retry/эскалации; режимы приёмки (auto/director/
  user); стратегии восстановления после сбоя.

## C07. Model Gateway (эволюция Model Router)

- **Назначение.** Выбор модели **и Runtime** под конкретную подзадачу в
  момент запуска. Этап 1.3 расширил C07 до Model Gateway (ADR-MAO-011):
  Runtime, Provider, Model, Employee и Session — раздельные понятия;
  сотрудник не привязан к модели/Runtime навсегда.
- **Ответственность.** Ведение каталога моделей (конфигурация: id, provider,
  tier, возможности, относительная стоимость, лимиты контекста);
  фильтрация по требованиям подзадачи (capabilityRequirements профессии +
  требования Skills); учёт доступности адаптеров C17 (модель считается
  кандидатом, только если доступен Runtime, её поддерживающий);
  расчёт финансовой категории источника (money / subscription / free /
  local — ADR-MAO-012); учёт качества (статистика model×profession×taskType
  через C14), сложности и риска задачи; эскалация при повторных попытках;
  запрет платных внешних API и платных fallback без разрешения.
- **Входы.** `SubtaskBrief` + `ProfessionProfile` + `SkillBundle` (оценка
  токенов), capabilities доступных Runtime (C17), статистика (C14), снимок
  бюджета (C08), цель слотов (C20).
- **Выходы.** `ModelSelection` (modelId, **runtimeId**, provider, финансовая
  категория, обоснование, fallback-цепочка, оценки стоимости для C08).
- **Взаимодействует с.** C05 (оценки), C06 (выбор при запуске), C08 (квоты и
  категории расходов), C01 (привязка сотрудника — намерение, не постоянная
  привязка), C14 (статистика), C17 (возможности Runtime).
- **Запрещено.** Запускать модели; менять каталог без команды C16; выбирать
  модель дороже необходимого уровня без записанного обоснования;
  автоматически переходить на платные источники; считать подписку
  API-балансом; скрывать от C08 категорию расхода.
- **Хранит.** Каталог моделей (конфигурационный файл `models.config.json` —
  источник истины; SQLite — кэш и статистика использования); отображение
  Provider → допустимые Runtime (подписка ChatGPT Plus закреплена за
  адаптером Codex, бесплатные opencode-go — за OpenCode).
- **Расширение.** Новые модели/провайдеры — записями каталога; новые
  Runtime — capabilities от C17 (без правки C07); политики выбора —
  стратегиями.

## C08. Budget Manager + Budget Guard (существующий `packages/budget-manager`)

- **Назначение.** Финансовый контроль: квоты, лимиты, журнал расходов.
  Этап 1.3 добавляет **Budget Guard** (ADR-MAO-012) — обязательный
  предстартовый фильтр и непрерывный контроль расхода по шести измерениям:
  реальные деньги (RUB), лимит подписки (ChatGPT Plus — число запросов и
  приблизительный расход контекста; **не** API-баланс), бесплатные квоты
  (наблюдаемый usage; факт квот провайдера не постулируется), число
  запросов, параллельные задачи (слоты), оценка контекста. Существующее ядро
  сохраняется; Guard — аддитивные интерфейсы политики.
- **Ответственность.** Атомарный допуск задачи (`startTask`), лимиты на
  задачу (стоимость/токены/длительность), месячные лимиты по агентам,
  учёт платежей, блокировка при исчерпании extra-бюджета, abort активных
  задач при блокировке, предоставление снимков состояния; Budget Guard:
  классификация потенциального расхода до запуска, отказ при нарушении
  лимитов (work slots и LLM-вызовы различаются), отсутствие автоматических
  платных fallback/пополнений.
- **Входы.** `TaskBudgetRequest` (через C06/C11, включая финансовую
  категорию от C07 и projectId), `UsageEventInput` (из исполнения),
  `CashPayment` (через C16), целевой лимит слотов (от C20 — единственный
  управляемый канал обновления политики).
- **Выходы.** `TaskHandle` (AbortSignal, release), `BudgetSnapshot`,
  `BudgetGuardDecision` (категория расхода, лимит, решение), ошибки
  `BudgetExceededError` и др.
- **Взаимодействует с.** C06 (координатор — единственный вызывающий допуска),
  C16 (снимки, платежи), C07 (категории расхода), C14 (журналы читаются для
  архивации, не наоборот).
- **Запрещено.** Получать prompt/тексты ответов/секреты (архитектурно
  гарантировано: принимает только метрики); запускать процессы; знать о
  содержимом задач; автоматически расходовать деньги (платный fallback/
  пополнение — только по явному действию пользователя); смешивать категории
  расходов (классификация — проекция политики, не вторая запись в ledger).
- **Хранит.** JSONL-журналы usage и платежей (`~/.local/share/open-agent-
  office/budget/`), in-memory ledger — источник истины финансов (ADR-MAO-003,
  не заменяется SQLite); классификация расходов — в состоянии политики.
- **Расширение.** Новые виды лимитов — полями политики (в т.ч. подписочные
  категории — аддитивно); per-project лимиты; интерфейс store уже позволяет
  иные реализации (в т.ч. SQLite-адаптер при будущей консолидации).

## C09. Context Manager

- **Назначение.** Сборка минимального достаточного контекста подзадачи.
- **Ответственность.** Формирование prompt-пакета: инструкции профессии,
  тела выбранных Skills (от C04), постановка подзадачи, релевантные
  артефакты-ссылки (от C13), краткая Project Memory (файл проекта),
  выдержки из истории по запросу; усечение по токен-бюджету; контроль, что
  полная история диалога не передаётся.
- **Входы.** `SubtaskBrief`, `ProfessionProfile`, `SkillBundle`, манифест
  артефактов (C13), Project Memory (файл), лимиты контекста модели (C07).
- **Выходы.** `ExecutionContext` (prompt, вложенные материалы, учётная
  оценка токенов).
- **Взаимодействует с.** C04, C07, C06, C13, C14 (выдержки из архива по
  запросу).
- **Запрещено.** Передавать полные истории сессий; включать секреты и
  содержимое исключённых файлов; превышать токен-бюджет без события
  `context_trimmed`.
- **Хранит.** Шаблоны сборки контекста; не хранит содержимое задач.
- **Расширение.** Стратегии сжатия/суммаризации (правила → LLM-summary как
  отдельная бюджетная операция); приоритеты секций контекста.

## C10. Session Manager

- **Назначение.** Управление сессиями исполнения сотрудников.
- **Ответственность.** Создание и возобновление сессий Runtime-адаптеров
  (OpenCode `sessionId` поддерживается C15; Codex — по capability C18;
  ADR-MAO-010); привязка сессии к сотруднику и задаче;
  политика «одна активная сессия на сотрудника»; восстановление после
  перезапуска (`sessionResume` — если адаптер поддерживает, иначе новая
  сессия с краткой передачей контекста через C09); закрытие и архивация
  сессий; изоляция сессий разных проектов. Сессия не привязывает сотрудника
  к модели или Runtime навсегда (ADR-MAO-011).
- **Входы.** Запросы исполнения (C06), идентификаторы сессий из событий
  Runtime (через координатор), команды отмены.
- **Выходы.** `SessionHandle` (sessionId, employeeId, projectId, состояние),
  события `session_opened/continued/closed`.
- **Взаимодействует с.** C06, C15 (через координатор), C01 (владелец сессии),
  C14 (история сессий).
- **Запрещено.** Парсить TUI; смешивать сессии разных сотрудников/проектов;
  хранить тексты переписки (тексты — в архиве C14, здесь только ссылки).
- **Хранит.** Реестр сессий (SQLite, `sessions`).
- **Расширение.** Пулы сессий; политики переиспользования; миграция сессий
  между моделями (новая сессия + краткая передача контекста через C09).

## C11. Concurrency Manager

- **Назначение.** Планирование очереди исполнений в пределах пула слотов.
- **Ответственность.** Очередь готовых подзадач (FIFO с приоритетами);
  распределение по слотам пула — **динамическая ёмкость**: стартовая планка
  2 LLM-исполнения, цель до 20 рабочих слотов (этап 1.3, ADR-MAO-014);
  фактический лимит одновременных LLM-вызовов задаёт политика C08 (значение
  готовит C20). Приоритизация (дедлайны, блокирующие подзадачи, интерактивные
  запросы пользователя); предотвращение голодания; немедленная реакция на
  `BudgetExceededError` (остановка приёма новых).
- **Входы.** Готовые подзадачи (C06), доступность слотов (через C08
  `maxConcurrentTasks`), целевое значение слотов (от C20 косвенно через
  политику C08), снимок бюджета.
- **Выходы.** Разрешение на запуск (делегируется координатору), события
  очереди (`task_queued/dequeued/slot_wait`).
- **Взаимодействует с.** C06, C08 (enforcement остаётся там — C11 только
  планирует), C20 (через политику), C16 (видимость очереди).
- **Запрещено.** Дублировать логику лимитов C08 (единый источник истины —
  политика бюджета через C20); запускать процессы; менять приоритеты без
  события.
- **Хранит.** Очередь (in-memory + зеркало в SQLite для восстановления).
- **Расширение.** Политики приоритетов; несколько пулов (например, отдельный
  пул для helper-задач) — если потребуется выше 20 слотов.

## C12. Result Validator

- **Назначение.** Автоматическая проверка результата подзадачи до приёмки.
- **Ответственность.** Выполнение критериев приёмки из плана: сначала
  детерминированные проверки (команды, тесты, линтеры, наличие файлов,
  схемы), затем — при необходимости — независимая LLM-проверка другим
  сотрудником (reviewer-профессия) как отдельное бюджетное исполнение;
  формирование вердикта (pass/fail/partial) с причинами; решение о retry.
- **Входы.** `SubtaskResult` (текст, артефакты, usage), критерии приёмки,
  политика валидации профессии.
- **Выходы.** `ValidationReport` (вердикт, выполненные проверки, причины,
  рекомендация retry/escalate/replan).
- **Взаимодействует с.** C06 (единственный вызывающий), C13 (артефакты),
  C07 (модель для LLM-проверки), C14 (журнал вердиктов).
- **Запрещено.** Помечать успешным результат, не прошедший обязательные
  критерии (принцип 13 AGENTS.md); модифицировать артефакты; повторно
  выполнять саму подзадачу (это решение C06).
- **Хранит.** Отчёты валидации (SQLite); шаблоны критериев.
- **Расширение.** Новые типы проверок — регистрацией check-плагинов;
  профили строгости по риску задачи.

## C13. Artifact Handoff

- **Назначение.** Передача результатов между подзадачами и вовне.
- **Ответственность.** Регистрация артефактов (файлы, diff, отчёты,
  изображения); манифест артефактов подзадачи; предоставление входных
  артефактов зависимым подзадачам (через C09 — ссылками и выдержками, не
  полным копированием в контекст); контроль целостности (хэши); связь
  артефактов с Git-историей проекта.
- **Входы.** Пути/манифесты от исполнения (C06), запросы зависимых
  подзадач, рабочая директория проекта.
- **Выходы.** `ArtifactManifest` (id, тип, путь, хэш, размер, источник),
  события `artifact_registered`.
- **Взаимодействует с.** C06, C09, C12, C14 (архивация ссылок; сами файлы —
  в ФС).
- **Запрещено.** Хранить бинарное содержимое в SQLite/контексте; передавать
  артефакты между проектами без явной команды; подменять рабочие директории.
- **Хранит.** Манифесты (SQLite, `artifacts`); файлы — в `projects/<id>/`.
- **Расширение.** Типы артефактов; внешние хранилища через адаптеры;
  политики удержания (retention).

## C14. Knowledge Manager

- **Назначение.** Постоянная память офиса: оперативный журнал + архив
  Obsidian.
- **Ответственность.** SQLite event store (все события до отображения и
  экспорта); транзакционный outbox; идемпотентный экспортёр Markdown в
  Obsidian vault (по docs/OBSIDIAN-ARCHIVE.md); связи между объектами
  (wikilinks); поисковый индекс; резервное копирование и восстановление;
  статистика успешности (usage × вердикты валидации) для C05/C07.
- **Входы.** События шины (C06), команды экспорта/поиска (C16), запросы
  статистики (C05/C07).
- **Выходы.** Подтверждения записи; Markdown-файлы в vault; результаты
  поиска; агрегаты успешности; отчёты целостности архива.
- **Взаимодействует с.** C06 (шина), C16 (API поиска/архива), C05, C07,
  C08 (читает его журналы для финансовой сводки, не записывает в них).
- **Запрещено.** Экспортировать событие до durable-записи в SQLite;
  архивировать секреты/токены/ключи (redaction на входе); изменять
  пользовательские заметки вне выделенных директорий vault (принцип 11
  AGENTS.md).
- **Хранит.** `office.db` (SQLite), outbox, поисковый индекс; файлы в
  vault — продукт экспорта.
- **Расширение.** Новые категории архива; шаблоны Markdown; альтернативные
  экспортёры (другой vault, формат) через интерфейс exporter.

## C15. OpenCode Runtime — адаптер (существующий `packages/runtime-opencode`)

- **Назначение.** Одна из реализаций контракта `RuntimeAdapter`
  (ADR-MAO-010, API_CONTRACTS §2.16) — исполнение одной LLM-задачи через
  OpenCode CLI. Этап 1.3 добавит обёртку-адаптер поверх существующего
  публичного API без его ломки (ядро сохраняется кодом и экспортами).
- **Ответственность.** Запуск `opencode run` с явной моделью и рабочей
  директорией; потоковый разбор JSONL-событий; агрегация usage;
  продолжение сессии; отмена по AbortSignal (SIGTERM→SIGKILL); таймауты;
  типизированные ошибки; редактирование секретов в событиях и stderr.
- **Входы.** `RuntimeTaskOptions` (model, prompt, cwd, title, sessionId,
  timeoutMs, signal, onEvent, onUsage) — только от координатора C06.
- **Выходы.** `RuntimeResult` (sessionId, text, events, exitCode, reason,
  usage) или типизированная ошибка.
- **Взаимодействует с.** Только координатором C06.
- **Запрещено.** Вызываться напрямую из других компонентов; обходить
  бюджетный допуск; выдавать несанкционированные данные наружу (redaction
  обязателен); интерактивный режим.
- **Хранит.** Ничего (stateless относительно вызовов; сессии хранит сам
  OpenCode CLI).
- **Расширение.** Новые адаптеры провайдеров — реализацией того же
  интерфейса `CoordinatorRuntime` (SDK/server-адаптер без переписывания
  C06, как зафиксировано в docs/ARCHITECTURE.md «Runtime strategy»).

## C16. Server API

- **Назначение.** Единая точка входа: HTTP + WebSocket для UI и локальных
  клиентов, жизненный цикл приложения.
- **Ответственность.** Эндпоинты задач (создание, статус, отмена), каталоги
  (сотрудники, профессии, отделы, Skills, модели), бюджет (снимок, платежи,
  статус подписки), поиск по архиву; WS-трансляция событий шины;
  аутентификация локальных клиентов (токен, идея `officeToken.ts`);
  привязка к 127.0.0.1; health check; конструирование компонентов при
  старте (composition root), включая регистрацию Runtime-адаптеров (C17)
  и активацию портфеля (C19).
- **Входы.** HTTP/WS-запросы клиентов; события шины C06.
- **Выходы.** JSON-ответы; поток событий; коды ошибок по контракту.
- **Взаимодействует с.** C05 (приём задач), C01/C02/C03/C07 (CRUD
  каталогов), C08 (снимки, платежи), C14 (поиск), C06 (статусы, отмены),
  C17 (статусы Runtime, этап 2), C19 (портфель, этап 2),
  UI `apps/office` (клиент).
- **Запрещено.** Слушать внешние интерфейсы; содержать бизнес-логику
  (только адаптер к компонентам); возвращать секреты и внутренние пути в
  ответах; обходить C08 через прямые вызовы Runtime.
- **Хранит.** Конфигурацию порта/токена (файлы `~/.agent-office/`),
  не бизнес-данные.
- **Расширение.** Версии API (`/v1/...`); новые ресурсы — новыми маршрутами
  к существующим компонентам; дополнительные клиенты (CLI, боты) — тем же
  контрактом.

## C17. Runtime Manager (модуль `packages/orchestrator`, этап 2)

- **Назначение.** Реестр Runtime-адаптеров и единая точка исполнения
  (ADR-MAO-010): один вызов — один подходящий адаптер, независимо от того,
  открыт ли он Codex'ом или OpenCode.
- **Ответственность.** Регистрация адаптеров (C15, C18); обнаружение и
  публикация capabilities (`supportedProviders/models`, `session`,
  `sessionResume`, `cancel`, `streamEvents`, `usage`, `adapterConcurrency`);
  выбор адаптера под (`modelId`, задача); унификация жизненного цикла:
  `RuntimeTask` → событие потока + `RuntimeResult`/типизированная ошибка;
  проверка capabilities конкретного адаптера перед использованием
  (наличие сессий/отмены/usage — capability, а не предположение);
  работоспособность = реестр статусов доступности адаптеров.
- **Входы.** `ModelSelection` (от C07 — modelId, runtimeId), `RuntimeTask`
  (от C06/C10), capability-запросы (C07), команды отмены.
- **Выходы.** Поток `RuntimeEvent` + `RuntimeResult` в едином формате;
  `RuntimeCapabilities[]` (для C07 и C16); события
  `runtime_adapter_registered/unavailable`.
- **Взаимодействует с.** C06 (исполнение), C07 (capabilities), C10
  (сессии), C15/C18 (адаптеры — только через контракт), C14 (события), C16
  (статусы адаптеров).
- **Запрещено.** Считать возможности адаптеров равными; вызывать адаптеры в
  обход контракта; хранить бизнес-состояние задач (это C06/C14); запускать
  адаптеры без финансового допуска C08.
- **Хранит.** Реестр адаптеров и их capabilities (in-memory, создаётся при
  старте из конфигурации C16), состояние доступности.
- **Расширение.** Новый адаптер — реализацией контракта и регистрацией;
  новые capabilities — полями `RuntimeCapabilities` (обратно совместимо).

## C18. Codex Runtime (`packages/runtime-codex`, этап 2)

- **Назначение.** Вторая независимая реализация `RuntimeAdapter`: исполнение
  задач через Codex с авторизацией поддерживаемой авторизации ChatGPT
  (подписка, ADR-MAO-012).
- **Ответственность.** Запуск задач Codex (унифицированное задание →
  собственный формат команд); парсинг собственного потока событий в
  `RuntimeEvent`; собственная иерархия типизированных ошибок; отмена;
  usage-метрики в унифицированном виде; сессии и их восстановление —
  только по каждой возможности (заявленная capability пакета).
- **Входы.** `RuntimeTask` (только от C17), настройки авторизации ChatGPT
  (через конфигурацию; секреты не хранятся в коде).
- **Выходы.** `RuntimeResult`, поток событий, usage; `RuntimeCapabilities`
  пакета.
- **Взаимодействует с.** Только C17 (по образцу «только координатор C06» для
  C15).
- **Запрещено.** Отдавать результаты в обход C17; считать сессии/usage
  обязательными без capability; расходовать подписку без допуска Budget
  Guard; принимать задачи напрямую от UI/API.
- **Хранит.** Ничего (stateless; сессии — на стороне Codex-клиента; ссылки —
  C10/C14).
- **Расширение.** Выделение универсальных частей в общий тестовый набор
  контракта адаптера (conformance tests в `runtime-opencode/testing` /
  `shared`).

## C19. Project Portfolio Manager (модуль `packages/orchestrator`, этап 2)

- **Назначение.** Реестр и политика одновременно активных проектов (2–5):
  что запускаем сейчас, что в ожидании, какой у проекта приоритет и лимиты
  (ADR-MAO-013).
- **Ответственность.** Портфель проектов (статусы: active/paused/quota-
  exhausted); per-project политики (бюджетная доля, лимит одновременных
  исполнений на проект, ограничение отделов/сотрудников); межпроектные
  решения о порядке задач; события `project_resumed/paused/quota_exceeded`.
- **Входы.** Реестр проектов (конфигурация C16 → SQLite `projects`, C14),
  бюджеты (C08), очередь/слоты (C11), команды пользователя.
- **Выходы.** Решения о допуске проекта к исполнению; приоритеты для C11;
  политики для C20; статусы для C16.
- **Взаимодействует с.** C16, C11, C20, C08 (per-project бюджеты), C14
  (история по проекту).
- **Запрещено.** Смешивать контексты проектов; запускать исполнения в обход
  C06/C08; хранить содержимое задач.
- **Хранит.** Портфель и политики per-project (SQLite).
- **Расширение.** Пул больше 5 проектов; приоритезация SLA; перенос
  проектов между рабочими машинами — будущий период.

## C20. Resource Allocator (модуль `packages/orchestrator`, этап 2)

- **Назначение.** Вычисление динамических ресурсов: целевого числа рабочих
  слотов (до 20) и их распределения между проектами (ADR-MAO-013/014).
- **Ответственность.** Единственный источник целевого лимита параллельности:
  учитывает бюджет/категории расходов (C08), capabilities и лимиты адаптеров
  (C17), очереди проектов (C19), нагрузку/прогресс задач; подаёт целевое
  значение в политику C08 (аддитивный канал), никогда не форсирует запуск.
- **Входы.** Снимки бюджета и подписки (C08), capabilities (C17), портфель
  (C19), агрегаты прогресса (C14).
- **Выходы.** Целевое число активных слотов и per-project квоты; события
  `resource_target_changed`.
- **Взаимодействует с.** C08 (подача целевого лимита), C17, C19, C11
  (использует фактическое значение через C08), C14.
- **Запрещено.** Менять политику C08 в обход единственного канала;
  «гарантировать» эмиссию 20 одновременных LLM-вызовов (число вызовов —
  производная бюджета и лимитов провайдеров); резервировать слоты.
- **Хранит.** Агрегаты решений (SQLite, «эвристики этапа 2 — простые
  правила», роста сложности/ML нет).
- **Расширение.** Адаптивные стратегии (правила → бюджет-ориентированные);
  интеграция с календарём maintenance окон.
