# MAO — SYSTEM OVERVIEW

Этапы 1.1–1.3 (MAO-ARCH-01/02/03). Общая архитектура Multi-Agent Office.
Этап 1.2 добавил контракты интерфейсов (API_CONTRACTS.md) и карту
реализации (IMPLEMENTATION_MAP.md); решения пользователя D-01–D-08
зафиксированы в ARCHITECTURE_DECISIONS.md. Этап 1.3 утвердил универсальную
архитектуру: несколько Runtime (OpenCode, Codex), Model Gateway,
подписочные финансы (ChatGPT Plus), многопроектность, динамический пул
слотов до 20.

Статус: проектная спецификация. Код на этих этапах не изменялся.

## 1. Назначение документа

Единая точка входа в архитектуру MAO: цели, принципы, карта компонентов,
их размещение в существующем монорепозитории и соответствие уже
реализованному коду. Детали — в профильных документах (раздел 9).

## 2. Цели системы

Локальный AI-офис на Debian — **универсальное приложение**:

- **Одно приложение → одно ядро → несколько независимых Runtime.** Codex и
  OpenCode — исполнительные движки за общим контрактом адаптера
  (ADR-MAO-010), а не отдельные приложения.
- Несколько бесплатных LLM-провайдеров + одна платная подписка ChatGPT
  Plus (ADR-MAO-012); обязательных платных API нет; месячный бюджет —
  до 2 000 ₽.
- Несколько одновременно активных проектов (2–5, ADR-MAO-013) с общей
  инфраструктурой и изолированными контекстами.
- Масштаб: 100+ специализированных сотрудников, 10–12 отделов, 30–40+
  профессий на старте (100+ профессий в перспективе), 100–200+ Skills.
- Динамический пул до 20 рабочих слотов; числом одновременных LLM-вызовов
  управляет финансовая политика (20 слотов ≠ 20 гарантированных вызовов).
- Obsidian — постоянный архив (ADR-005, KNOWLEDGE_ARCHIVE.md).
- Экономика: дешёвая модель по умолчанию, эскалация только по обоснованию,
  никаких автоматических платных fallback и пополнений.

## 3. Принципы

1. **Профессия ≠ процесс модели.** Профессия — декларативный профиль
   компетенций и ответственности (данные). Исполнение — кратковременный
   запуск Runtime-адаптера, занимающий рабочий слот пула.
2. **Расширение регистрацией.** Новые профессии, отделы, Skills, модели,
   Runtime и проекты добавляются файлами-описаниями и записями реестров;
   ядро не переписывается.
3. **Совместимость с существующим кодом.** `runtime-opencode`,
   `budget-manager` и координатор `orchestrator` сохраняются как ядро
   исполнения и финансового контроля; API C08/C15 не ломаются.
4. **Runtime-нейтральность.** Ни один компонент ядра не знает срок
   особенности конкретного CLI: всё через `RuntimeAdapter` и его
   capabilities (ADR-MAO-010).
5. **Дешевизна сначала.** Никакие операции, выполнимые детерминированными
   инструментами, не отправляются в LLM.
6. **Локальность.** Все сервисы на 127.0.0.1; секреты не покидают машину;
   редактирование секретов — на уровне Runtime (уже реализовано).
7. **Простая задача — один специалист.** Обязательного участия всех
   сотрудников нет; состав команды определяется задачей.
8. **Сначала архив, потом показ.** События фиксируются в оперативном
   хранилище до экспорта в Obsidian и до отображения в UI.

## 5. Потоки данных (сводно)

### 5.1. Путь задачи (command flow)

```
Пользователь → C16 Server API → C05 Task Router
  → C02 Profession Registry (подбор профессий; отделы — фильтр)
  → C19 Project Portfolio Manager (приоритеты и лимиты проекта)
  → C04 Skill Resolver → C03 Skill Registry (подбор Skills)
  → C07 Model Gateway (модель + runtimeId под подзадачу)
  → C09 Context Manager (минимальный контекст, изоляция проекта)
  → C06 Orchestrator → C20 Resource Allocator (целевое число слотов)
  → C11 Concurrency Manager → C08 Budget Manager (слот, Budget Guard)
  → C10 Session Manager → C17 Runtime Manager → C15/C18 адаптер (исполнение)
  → C13 Artifact Handoff (передача результатов между подзадачами)
  → C12 Result Validator (проверка, повторные попытки)
  → C06 (финальная приёмка Director-профилем при необходимости)
  → C14 Knowledge Manager (архив)
```

Подробный жизненный цикл и fast path для простых задач — TASK_LIFECYCLE.md.

### 5.2. Поток событий (event flow)

Все компоненты публикуют типизированные события в шину событий C06
(in-process EventEmitter; типы — `packages/shared`). Подписчики:

- C14 Knowledge Manager — дurable-запись (SQLite → outbox → Obsidian);
- C16 Server API — трансляция в WebSocket для UI;
- C08 Budget Manager — usage-события от C15 (уже реализовано через
  `onUsage` координатора, сохраняется).

Семантика доставки: C14 подписан первым (durable-first — событие
показывается только после записи в SQLite); ошибка недюрабельного
подписчика не останавливает остальных; события идемпотентны по `eventId`
(повторная публикация не создаёт дубликатов). Контракт —
API_CONTRACTS §2.15.

### 5.3. Хранение

| Слой | Технология | Владелец | Содержимое |
| --- | --- | --- | --- |
| Оперативное состояние | SQLite (`~/.local/share/open-agent-office/office.db`) | C14 | задачи, события, сессии, реестры-кэш, outbox |
| Финансовый журнал | JSONL (`.../budget/*.jsonl`) | C08 (реализовано) | usage-записи, платежи — append-only ledger |
| Долговременный архив | Markdown (Obsidian vault) | C14 | проекты, задачи, решения, отчёты, артефакты |
| Рабочие данные | Файловая система (`projects/<id>/`) | C13 | код, артефакты, Git-история |
| Определения | Файлы в репозитории | C02/C03 | `professions/*.md`, `skills/**/SKILL.md` |

Обоснование двойного хранения (SQLite + JSONL) — ADR-MAO-003 в
ARCHITECTURE_DECISIONS.md.

## 6. Соответствие существующему коду

Сохраняется без изменений интерфейса:

- `OpenCodeRuntime.runTask()` (C15): модель, prompt, cwd, title, sessionId,
  AbortSignal, потоковые события, usage-дельты, типизированные ошибки,
  редактирование секретов. Этап 2 добавляет адаптерную обёртку
  `RuntimeAdapter` поверх этого API без его ломки (ADR-MAO-010).
- `BudgetManager` (C08): `startTask/recordUsage/releaseTask`, лимиты на
  задачу и на агента, `maxConcurrentTasks`, блокировка по платежам.
  Этап 2: Budget Guard добавляется аддитивно (новые интерфейсы политики,
  ADR-MAO-012), существующий контракт не ломается.
- `AgentExecutionCoordinator` (ядро C06): связка C08+C15 для одного
  исполнения, `cancelTask`, упорядоченная запись usage.
- `DEFAULT_AGENT_MODELS` в `packages/orchestrator/src/agents.ts`:
  сохраняется как **таблица назначений по умолчанию**, питающая C01/C07
  при инициализации (см. ADR-MAO-004 и зафиксированное противоречие P-01
  в ARCHITECTURE_DECISIONS.md).

Расширяется (новые модули, не переписывание): планировщик, retry-циклы,
контекст, сессии, артефакты — модули `packages/orchestrator`.

Замечание этапа 1.2: публичные API C15 (`runTask`, типы) и C08
(`startTask`, `recordUsage`, `getSnapshot` и др.) не расширялись и не
менялись; контракт зафиксирован как стабильный в API_CONTRACTS §2.13–2.14.
Финансовый учёт C08 остаётся на JSONL (ADR-MAO-003).

Заменяется на уровне интеграции (не ядра): клиентский протокол UI
(`useAgentSocket` и связанные модули `apps/office`) будет подключён к
новому C16 на следующих этапах; UI в рамках этапов 1.1–1.2 не изменяется.

## 7. Известные противоречия текущей реализации

Полный реестр с предлагаемыми решениями — ARCHITECTURE_DECISIONS.md,
раздел «Зафиксированные противоречия» (P-01…P-06). Кратко:

- P-01: координатор запрещает `modelId` в запросе задачи, а целевая
  архитектура выбирает модель под задачу.
- P-02: `DEFAULT_MAX_CONCURRENT_TASKS = 1`, целевое — 2.
- P-03: ROADMAP отмечает Stage 1/2 выполненными (SQLite, health endpoint),
  кода нет.
- P-04: пять жёстко заданных агентов вместо реестра профессий.
- P-05: протокол UI привязан к несуществующему внешнему серверу.
- P-06: журналы бюджета — JSONL, а ADR-005 назначает SQLite хранилищем
  событий (разрешено разделением ответственности, ADR-MAO-003).

## 8. Нефункциональные требования

- Тестируемость: каждый компонент C01–C20 имеет интерфейс, допускающий
  fake-реализацию (по образцу инжекции `spawn` в C15); сквозные сценарии до
  подключения платных моделей прогоняются на Fake Runtime (для каждого
  адаптера — собственный fake; ADR-MAO-010).
- Восстановление: состояние задач и сессий переживает перезапуск процесса
  (SQLite + журналы); незавершённые задачи переводятся в восстановимый
  статус; восстановление сессии — если адаптер заявил `sessionResume`.
- Наблюдаемость: все переходы состояний — события с ID задачи, сотрудника,
  модели, runtime, проекта; usage доступен по agent/model/task/project/
  session (уже поддержано схемой C08).
- Безопасность: 127.0.0.1, токен доступа к Server API, redaction секретов на
  границе Runtime, подтверждение деструктивных действий (сбалансированный
  режим из AGENTS.md), enforcement через права ОС и изоляцию рабочих
  директорий.
- Масштабируемость: 100+ сотрудников и 10–12 отделов без деградации
  (реестры + пагинация API); 2–5 проектов с изоляцией (ADR-MAO-013);
  динамический пул до 20 рабочих слотов под управлением C20 (ADR-MAO-014).
