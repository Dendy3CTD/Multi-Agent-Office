# MAO — ARCHITECTURE DECISIONS

Принятые решения (ADR-MAO-*) и реестр противоречий текущей реализации
(P-01…P-06). Дополняет, а не отменяет `docs/DECISIONS.md` (ADR-001…006
остаются в силе, кроме случаев явной увязки ниже).

---

## ADR-MAO-001. Профессия как данные, сотрудник как запись реестра

**Контекст.** Цель — 30–40+ профессий, динамическая регистрация, независимость
от числа LLM-процессов.

**Решение.** Профессии — файлы `professions/*.md` с фронтматтером; сотрудники
— записи C01 в SQLite; исполнение — кратковременные запуски C15 через пул
слотов. Профессия не является процессом; сотрудник «работает» только во время
Execution.

**Последствия.** Масштабирование до 100+ профессий — добавлением файлов.
Требуется новый пакет `packages/directory`. Существующие пять записей
`DEFAULT_AGENT_MODELS` становятся начальными данными реестра.

**Статус:** принято (D-01, этап 1.2).

## ADR-MAO-002. Skills как Markdown-файлы SKILL.md с прогрессивной загрузкой

**Решение.** Формат `skills/**/SKILL.md` (фронтматтер + тело), реестр-индекс
в SQLite, резолвер C04 выбирает ≤ 5 Skills / ~4000 токенов на исполнение.
Формат совместим с экосистемными SKILL.md (переиспользование материалов).

**Последствия.** Никогда не передаём весь каталог в контекст. Требуется
`packages/skills`. Пустые каталоги `skills/roles/*` — заготовки; канонические
id профессий определяются в `professions/` (см. EMPLOYEE_SYSTEM.md §8).

**Статус:** принято (этап 1.2; D-04).

## ADR-MAO-003. Два хранилища: SQLite (события) + JSONL (финансы)

**Контекст.** ADR-005 назначает SQLite хранилищем событий; существующий C08
реализован на append-only JSONL-журналах и покрыт тестами.

**Решение.** Финансовый ledger C08 остаётся на JSONL (неизменяемый журнал —
свойство, а не недостаток). Оперативное состояние и события — в SQLite
(`packages/archive`). SQLite содержит зеркало usage (идемпотентный импорт по
eventId) для агрегатов и статистики. Переписывать C08 не требуется.

**Последствия.** ADR-005 уточняется: SQLite — источник истины задач/событий;
JSONL — источник истины финансового учёта. Отказ от миграции журналов
устраняет риск потери финансовой истории.

**Статус:** принято (этап 1.2; JSONL-учёт C08 сохраняется, разрешает P-06).

## ADR-MAO-004. Модель выбирает Model Router; запрет пользовательского modelId сохраняется

> Этап 1.3: компонент расширен до **Model Gateway** (ADR-MAO-011); запрет
> пользовательского modelId и механизм сохраняются без изменений.

**Контекст.** Координатор отклоняет `modelId` в запросе задачи
(`InvalidTaskRequestError`, см. P-01); цель — выбор модели под задачу.

**Решение.** Вводится C07 как единственный поставщик `modelId` для
координатора. Пользователь по-прежнему не может навязать модель; сотрудник
имеет `modelDefault` как нижнюю границу. На уровне кода это означает, что при
реализации запрос координатора получает вычисленный `modelId` от C07 — либо
через расширение `AgentTaskRequest` (новое поле с проверкой происхождения),
либо через временную регистрацию соответствия agent→model. Конкретный
механизм — решение этапа реализации, здесь фиксируется только контракт.

**Последствия.** Обратная совместимость валидации сохраняется для внешних
вызывающих; `DEFAULT_AGENT_MODELS` остаётся fallback.

**Уточнение (этап 1.2, API_CONTRACTS §2.5.2).** Повторы и эскалация не
включают модели с `paidExternal: true` ни в селекцию, ни в fallback-цепочку:
автоматический переход на платные внешние API исключён; доступ к ним —
только по явному разрешению пользователя на конкретную операцию.

**Статус:** принято (этап 1.2; разрешает P-01).

## ADR-MAO-005. Параллельность: планирование в C11, enforcement в C08, лимит 2

**Решение.** Единственный механизм принудительного ограничения слотов —
`maxConcurrentTasks: 2` в политике C08 (заменяет текущий дефолт 1,
противоречие P-02). C11 — очередь и приоритеты, не дублирует логику лимитов.
Один сотрудник — одно исполнение одновременно.

**Уточнение (этап 1.2, API_CONTRACTS §2.9).** Атомарное резервирование слота:
выдачу из очереди C11 выполняет единственный диспетчер C06; слот
резервируется только успешным `startTask` C08 (in-memory ledger + файловая
блокировка), поэтому двойное выделение исключено; при отказе допуска
подзадача возвращается в очередь без потери приоритета. Интерактивные
задачи получают приоритет впереди очереди `normal`, но отдельного слота
нет (D-06); вытеснение выполняющихся исполнений приоритетом не допускается.

**Редакция (этапы 1.3–1.4, ADR-MAO-014).** Позиция «отдельного слота нет»
относилась к фиксированному пулу из 2 слотов и аннулирована вместе с этой
фиксацией: пул эластичен (старт 2 → до 20 рабочих слотов, D-05 в
окончательной формулировке). Выделенных резервных слотов по-прежнему нет;
интерактивный приоритет и запрет вытеснения сохраняются; фактическую
параллельность LLM определяют доступность Runtime, квоты и ограничения
(Budget Guard).

**Статус:** принято (D-05/D-06, этап 1.2; разрешает P-02).

## ADR-MAO-006. Server API как composition root, без бизнес-логики

**Решение.** `apps/server` конструирует компоненты C01–C15 и предоставляет
HTTP/WS-адаптер (127.0.0.1, токен по образцу `officeToken.ts`). API
версионируется (`/v1/`). Бизнес-правила живут только в пакетах.

**Статус:** принято (этап 1.2).

## ADR-MAO-007. Приёмка: детерминированные проверки вперёд, LLM-review по политике

**Решение.** C12 сначала исполняет проверки инструментами (без токенов);
LLM-review — отдельное бюджетное исполнение другим сотрудником, только если
`acceptancePolicy` профессии/задачи требует. Успех не объявляется до прохождения
обязательных критериев (принцип 13 AGENTS.md). Director-приёмка — только для
complex-задач.

**Статус:** принято (этап 1.2).

## ADR-MAO-008. Событийная шина in-process, durable-запись до отображения

**Решение.** Шина — типизированный EventEmitter в C06 (типы в
`packages/shared`). Порядок потребления гарантирует: C14 (SQLite) подписывается
синхронно до C16 (WS/UI). События несут ids задачи/сотрудника/модели; payload
проходит redaction.

**Последствия.** UI никогда не показывает событие, которое не переживёт
перезапуск. Будущий вынос компонентов в отдельные процессы потребует замены
шины на транспорт — интерфейс подписок это допускает.

**Уточнение (этап 1.2, API_CONTRACTS §2.15).** Ошибка недюрабельного
подписчика не останавливает доставку другим (событие `subscriber_failed`).
Ошибка durable-записи C14 — останавливает: событие не показывается, пока
не зафиксировано в SQLite; публикующий компонент повторяет публикацию.
События идемпотентны по `eventId`: повторная публикация не создаёт
дубликатов в C14, зеркале usage и outbox.

**Статус:** принято (этап 1.2).

## ADR-MAO-009. Universal Core: одно ядро, фиксированные роли пакетов

**Контекст.** Цель универсального приложения (этап 1.3): несколько Runtime
(Codex, OpenCode), несколько бесплатных провайдеров, одна платная подписка,
100+ сотрудников, 10–12 отделов, 2–5 проектов. Принцип: **одно приложение →
одно ядро → несколько независимых Runtime** — Codex и OpenCode являются
исполнительными движками, а не отдельными приложениями.

**Решение.** Роли пакетов фиксированы:

- `packages/shared` — типы, события, контракты адаптеров; единственный пакет
  без зависимостей;
- `packages/directory` — C01 (сотрудники, отделы) + C02 (профессии);
- `packages/skills` — C03/C04;
- `packages/archive` — C14;
- `packages/model-manager` — C07 (Model Gateway);
- `packages/budget-manager` — C08 + Budget Guard (§ ADR-MAO-012);
- `packages/orchestrator` — C05/C06, C09–C13, C17 Runtime Manager,
  C19 Portfolio Manager, C20 Resource Allocator;
- `packages/runtime-opencode` — существующий C15 (сохраняется);
- `packages/runtime-codex` — новый C18 (этап 2), только контракт адаптера;
- `apps/server` — C16 (composition root), ничто не импортирует его.

Циклические зависимости запрещены; целевой граф — IMPLEMENTATION_MAP §5
(этап 1.3): реестры не импортируют orchestrator; runtime-адаптеры реализуют
контракт из `shared` и импортируются только orchestrator'ом.

**Статус:** принято (этап 1.3).

## ADR-MAO-010. Runtime-адаптеры: единый контракт, независимые возможности

**Решение.**

- Общий контракт `RuntimeAdapter` объявляется в `packages/shared`
  (API_CONTRACTS §2.16): `execute(task: RuntimeTask, callbacks): Promise<RuntimeResult>`,
  поток событий, `cancel()`, capabilities. Унифицированные типы задания
  (`RuntimeTask`), результата (`RuntimeResult`) и ошибок — тоже в shared.
  Существующий публичный API C15 (`OpenCodeRuntime.runTask` и типы) не
  меняется; адаптер C15 реализует `RuntimeAdapter` поверх него без
  переименований (без рефакторинга ядра).
- **C15 OpenCode Runtime** (`packages/runtime-opencode`) — сохраняется.
- **C18 Codex Runtime** (`packages/runtime-codex`, этап 2) — отдельный
  адаптер; авторизация через поддерживаемую авторизацию ChatGPT (ADR-MAO-012),
  собственный парсер событий, собственные типизированные ошибки.
- **C17 Runtime Manager** (модуль `packages/orchestrator`): реестр адаптеров,
  обнаружение и публикация возможностей (`capabilities`: поддерживаемые
  модели/провайдеры, сессии и их восстановление (sessionResume), отмена,
  потоковые события, usage, лимиты параллельности адаптера), выбор адаптера
  для исполнения по паре (modelId, задача), унификация жизненного цикла
  (запуск/события/отмена/ошибки/временные границы).
- **Возможности Codex и OpenCode не предполагаются идентичными:** каждое
  поведение опционально и объявляется capability; вызывающие проверяют
  capability до использования (fallback к общему знаменателю: запуск,
  результат, отмена, типизированные ошибки). Восстановление сессий — только
  при `sessionResume: true`; иначе сессия открывается заново с передачей
  краткого контекста через C09.

**Статус:** принято (этап 1.3).

## ADR-MAO-011. Model Gateway: отделение Runtime, Provider, Model, Employee, Session

**Контекст.** Этап 1.1/1.2 привязывал выбор модели к C07 без учёта Runtime.
Этап 1.3 требует, чтобы сотрудник не был привязан к модели или Runtime
навсегда.

**Решение.** C07 расширяется до **Model Gateway** и содержит разделение
понятий:

- **Runtime** — исполнительный адаптер (OpenCode / Codex), не источник
  моделей и не собственность сотрудника;
- **Provider** — источник моделей (пул бесплатных opencode-go, подписка
  ChatGPT Plus для Codex, будущие; `paidExternal` остаётся запрещённым
  без разрешения);
- **Model** — запись каталога (`models.config.json`: id, provider,
  capability, стоимость, ограничения контекста);
- **Employee** — субъект с назначением; привязка сотрудника к модели или Runtime
  — временная, на исполнение; `modelDefault` — нижняя граница и резерв
  (сохраняется семантика §2.5.1 API_CONTRACTS);
- **Session** — исполнительная связь сотрудник+проект+адаптер; не привязывает
  сотрудника к модели навсегда.

Модель выбирается с учётом: задачи и её сложности, качества (статистика
C14), доступности (enabled/availability), ограничений (контекст, политика),
стоимости (включая финансовую категорию источника — ADR-MAO-012) и
возможностей Runtime (только модели, поддерживаемые доступным адаптером
C17). Результат `ModelSelection` содержит и модель, и `runtimeId`.

**Статус:** принято (этап 1.3).

## ADR-MAO-012. Финансовая архитектура: подписки, Budget Guard, запрет авторешений

**Контекст.** Бюджет пользователя — максимум 2 000 ₽/мес. Схема: одна
подписка ChatGPT Plus; Codex — через поддерживаемую авторизацию ChatGPT;
OpenCode — бесплатные модели; локальные инструменты; обязательных платных
API нет.

**Решение.**

- **ChatGPT Plus — не API-баланс.** Подписка учитывается как ежемесячный
  фиксированный платёж (money-category платежа C08) и как ограничение
  использования (число запросов и приблизительный расход контекста).
  Точные токенные квоты подписки не постулируются; лимит числа запросов —
  наблюдаемая политика пользователя, а не факт квоты провайдера.
- **Кросс-привязка запрещена:** подписочная авторизация Codex недоступна
  OpenCode и наоборот; провайдер подписки закреплён за адаптером.
- Budget Manager различает пять категорий (DATA_MODEL §2.6): реальные
  денежные расходы (RUB, JSONL ledger), ограничения подписки (requestCount,
  approxContextTokens), бесплатные квоты (наблюдаемый usage, факт квоты
  провайдера не постулируется), число запросов, параллельные задачи
  (слоты). Приблизительный расход контекста — оценка из C09/C07.
- **Budget Guard** — обязательный предстартовый gate C08 (расширенный
  `startTask`-порядок: классификация потенциального расхода по категориям,
  сопоставление с лимитами, отказ/пропуск + непрерывный контроль
  во время исполнения). Контракт — аддитивное расширение C08, существующий
  публичный API не ломается.
- **Никаких автоматических платных fallback и пополнений:** эскалация модели
  никогда не переходит к платному источнику без явного подтверждения
  пользователя на конкретную операцию (соответствует §1 MODEL_ROUTING);
  исчерпание подписки/бюджета блокирует новые исполнения, а не тратит деньги.

**Последствия.** ADR-MAO-003 сохраняется: JSONL ledger не заменяется SQLite;
двойной учёт исключён (категории — проекция/классификация в политике,
не вторая запись в ledger).

**Статус:** принято (этап 1.3).

## ADR-MAO-013. Многопроектность: Portfolio Manager и Resource Allocator

**Решение.** 2–5 параллельных проектов с изоляцией (рабочие директории
`projects/<id>/`, отдельные сессии, контексты, история и per-project
бюджетные доли) и общим пулом специалистов:

- **C19 Project Portfolio Manager** (модуль `packages/orchestrator`):
  реестр проектов, приоритеты, per-project политики (бюджетная доля,
  лимит исполнений на проект), межпроектные решения о порядке;
- **C20 Resource Allocator** (модуль `packages/orchestrator`): вычисляет
  целевое число рабочих слотов (динамическая параллельность, ADR-MAO-014) и
  распределение ресурсов между проектами; это единственный источник
  целевого лимита. C08 остаётся enforcement'ом: значение подаётся
  в C08 как значение политики (аддитивный канал обновления, см.
  API_CONTRACTS §2.13); C11/C06 лимиты не меняют.

Изоляция контекстов — C09 (Project Memory по проекту, без смешивания);
независимая история — архив C14 по projectId (уже поддержано схемой).

**Статус:** принято (этап 1.3).

## ADR-MAO-014. Масштаб организации и динамическая параллельность (пересмотр D-05/D-06)

**Контекст.** Этапы 1.1–1.2 фиксировали пул «до 2 одновременных LLM-
исполнений» (в реестре — D-05; в задании этапа 1.3 это решение обозначено
как D-04 — имеется в виду то же ограничение параллельности). Новые цели:
100+ сотрудников, 10–12 отделов, до 20 рабочих слотов.

**Решение.**

- **Рабочие слоты (work slots) ≠ одновременные LLM-вызовы.** До 20 слотов
  описывают ёмкость офиса (активных исполнений с подготовкой/проверкой/
  ожиданием), фактический лимит одновременных LLM-вызовов задаётся
  финансовой политикой (ADR-MAO-012) и возможностями адаптеров/провайдеров
  (C17): у бесплатных провайдеров и подписки свои ограничения.
- Стартовая политика консервативна (2 LLM-исполнения, текущий дефолт C08),
  рост вычисляется C20 по бюджету/квотам/нагрузке; enforcement остаётся
  в C08. «Гарантированных 20 одновременных вызовов» не существует.
- **D-05 пересмотрен:** фикс «2» заменён на «старт 2, динамическая цель
  до 20, вычисляемая политикой». **D-06 сохраняется в сути:** интерактивные
  задачи — приоритет в общей очереди, вытеснения нет; «отдельного слота»
  больше не постулируется, поскольку пул эластичен (никакого резервного
  слота нет — формулировка «без третьего слота» аннулирована как привязанная
  к фиксированному пулу).
- Отделы: `Department` — группировка профессий (DATA_MODEL §2.1); 10–12
  отделов как справочная структура приёмки орг-отчётов и фильтрации.

**Статус:** принято (этап 1.3; пересматривает фиксацию формулировки D-05:
два LLM-исполнения — стартовая планка, не потолок).

## Решения, требовавшие согласования с пользователем (закрыты D-01…D-08)

1. Новый пакет `packages/directory` (C01/C02) — вместо размещения реестров
   внутри orchestrator. Альтернатива: модули orchestrator.
   → **Закрыто D-01: отдельный пакет.**
2. Каталоги `skills/roles/{lawyer,coder,modeller}` не входят в целевой список
   профессий — архивировать или переименовать при наполнении?
   → **Закрыто D-04: сохранить до проверки наполнения.**
3. Дефолтное число слотов пула: 2 подтверждено заданием; нужен ли отдельный
   резервный слот для интерактивных команд пользователя?
   → **Закрыто D-05 и D-06: два слота; отдельного нет — приоритет в общей очереди.**
   → **Пересмотрено этапом 1.3 (ADR-MAO-014): пул динамический до 20 слотов,
   «2» — стартовая планка; формулировка «отдельного слота нет» заменена
   эластичным пулом. Число LLM-вызовов лимитируется финансовой политикой.**
4. Политика архивации текстов prompt/ответов (KNOWLEDGE_ARCHIVE §7):
   по умолчанию — только ссылки и выдержки. Подходит ли это для нужд отладки?
   → **Закрыто D-07: режим метаданных по умолчанию.**
5. Порог success-rate 0.6 для понижения дешёвых моделей (MODEL_ROUTING §3) —
   стартовое значение, подлежит калибровке на реальных данных.
   → **Закрыто D-08: порог подтверждён как стартовый; добавлены минимальная
   выборка и категория задачи.**

## Открытые вопросы (этап 1.3, не блокируют подэтап 1.4)

1. **Механизм авторизации Codex через ChatGPT Plus.** Конкретная схема
   (CLI-сессия, OAuth-флоу, cookie/token-набор) фиксируется при реализации
   `packages/runtime-codex` (волна S2-3); до проверки прода-сессии
   capabilities Codex задаются консервативно.
2. **Реальные лимиты подписки ChatGPT Plus.** Заранее не постулируются
   (ADR-MAO-012); политики requestCount/approxContextTokens задаются
   пользователем и калибруются наблюдением.
3. **Канал обновления политики C08 (аддитивный).** Форма (политики-апдейтера vs
   injectable `slotLimitSource`) — решение волны S2-5/7; публичные методы
   ядра C08 не ломаются.
4. **Полноправный переход координатора на C17.** Прямой путь C06→C15
   сохраняется до валидации conformance-тестов (волна S2-2); переключение —
   на S2-9.
5. **Калибровка целевых слотов.** Простые правила этапа 2 (волна S2-7);
   адаптивные стратегии — после пилотных прогонов.
