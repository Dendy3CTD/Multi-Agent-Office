# MAO — MODEL ROUTING / MODEL GATEWAY

Выбор моделей и Runtime (C07 Model Gateway) и контроль расходов
(совместно с C08 и C20). Размещение: `packages/model-manager` (сейчас
пустой каталог).

## 1. Принципы

1. Модель выбирается **под подзадачу в момент запуска**, а не закрепляется
   навсегда за профессией или сотрудником. Привязка сотрудника
   (`modelDefault`) — только нижняя граница и запасной вариант (ADR-MAO-011).
2. Сначала рассматривается самая дешёвая подходящая модель.
3. Более сильная модель — только по обоснованной необходимости (требования
   возможностей, провал предыдущих попыток, риск задачи), обоснование
   записывается событием.
4. Платные внешние API (`paidExternal: true`) запрещены без отдельного
   разрешения пользователя на конкретную операцию.
5. Операции, выполнимые инструментами, модели не поручаются.
6. **Runtime-нейтральность (этап 1.3):** кандидаты рассматриваются только
   среди моделей, поддерживаемых доступным адаптером (C17); возможности
   Codex и OpenCode не предполагаются равными (ADR-MAO-010).

## 1a. Разделение понятий (ADR-MAO-011)

| Понятие | Что это | Кто владеет | Связи |
| --- | --- | --- | --- |
| Runtime | Исполнительный адаптер (OpenCode C15, Codex C18) | C17 (реестр) | исполняет `RuntimeTask`; capabilities; не источник моделей |
| Provider | Источник моделей (пул opencode-go бесплатно; ChatGPT Plus — подписка) | C07 (каталог) | закреплён: ChatGPT Plus → Codex; opencode-go → OpenCode; кросс-привязка запрещена |
| Model | Запись каталога (id, provider, tier, возможности, ограничения) | C07 | выбирается на исполнение |
| Employee | Субъект офиса (запись C01) | C01 | не привязан к модели/Runtime навсегда; `modelDefault` — нижняя граница и резерв |
| Session | Исполнительная связь employee+project+адаптер | C10 | не фиксирует модель навсегда; независима между проектами |

Модель выбирается с учётом: задачи и сложности, качества (ModelStats),
доступности (enabled + availability адаптера), ограничений (контекст,
политика, `paidExternal`), стоимости (включая категорию расхода:
money/subscription/free/local — ADR-MAO-012) и возможностей Runtime.

## 2. Каталог моделей

Файл `models.config.json` (источник истины), схема `ModelDescriptor` —
в DATA_MODEL.md. Начальное содержимое — по фактической таблице OAO-MODEL-002:

| modelId | provider | tier | capabilities | примечание |
| --- | --- | --- | --- | --- |
| opencode-go/beam-free | opencode-go | free | text, light | helper-задачи, суммаризации |
| opencode-go/mimo-v2.6-flash | opencode-go | cheap | code, reasoning | director/analyst по умолчанию |
| opencode-go/glm-5.3-flash | opencode-go | cheap | code | developer по умолчанию |
| opencode-go/qwen3.8-flash | opencode-go | cheap | code, reasoning | engineer по умолчанию |

Каталог расширяется записями (новые бесплатные модели OpenCode Go, модели
ChatGPT Plus для Codex — этап 2, категория `subscription`; будущие версии).
Категории `tier` упорядочены: free < cheap < standard < strong. Новое поле
этапа 1.3: `runtimeId` / `supportedRuntimes` — допустимые Runtime для модели
(по capabilities от C17; заполняется C17 при инициализации и хранится в
каталоге).

## 3. Алгоритм выбора (при запуске подзадачи)

Вход: `SubtaskBrief` + `ProfessionProfile` + `SkillBundle` (оценка токенов)
+ снимок бюджета C08 (включая подписочные категории) + ModelStats +
capabilities доступных Runtime (C17).

1. **Фильтр Runtime.** Остаются только модели, поддерживаемые доступным
   адаптером (`RuntimeCapabilities` от C17, этап 1.3: одна реализация —
   C15/opencode-go, что эквивалентно прежнему поведению).
2. **Фильтр возможностей.** Остаются модели, удовлетворяющие
   `capabilityRequirements` профессии и `requiredTools`-требованиям Skills
   (например, long-context для большого входа).
3. **Фильтр границы сотрудника.** `modelDefault` сотрудника задаёт
   минимально допустимый уровень (API_CONTRACTS §2.5.1): кандидаты с tier
   ниже уровня `modelDefault` или без имеющихся у него capabilities
   отбрасываются. Понижать уровень относительно модели сотрудника ради
   дешевизны запрещено.
4. **Фильтр контекста.** `maxContextTokens` ≥ оценки входа (контекст C09 +
   ожидаемый выход). Не подходит — отбрасывается с записью причины.
5. **Фильтр политики.** `paidExternal` — отбрасываются без разрешения;
   `enabled: false` — отбрасываются; модели подписки — только в рамках
   лимитов подписки C08 (ADR-MAO-012).
6. **Ранжирование.** Сортировка по (финансовая категория, tier,
   relativeCost) — дешевле/«бесплатнее» выше: free < subscription (в
   пределах лимита подписки: «уже оплачено») < paid. Корректировка
   историей: если у дешёвой модели success-rate по паре
   (modelId, professionId, taskType) ниже порога (стартовое значение 0.6,
   настраивается; учитывается минимальная выборка и категория задачи —
   D-08), она понижается в ранге или исключается; данные — ModelStats
   (DATA_MODEL.md).
7. **Выбор.** Первая в ранге. Результат: `ModelSelection` (modelId,
   runtimeId, provider, финансовая категория, обоснование,
   fallback-цепочка — следующие 1–2 кандидата; `modelDefault`
   сотрудника — резервный вариант и последний элемент цепочки).
8. **Оценки для бюджета.** estimatedCostUsd/estimatedTotalTokens/
   estimatedDurationMs и категория расхода передаются в `startTask` C08.

## 4. Эскалация и повторные попытки

Порядок правил при повторах нормирован в API_CONTRACTS §2.5.2; кратко:

- Попытка 1: полный алгоритм §3 (с фильтром границы сотрудника).
- **Повтор той же модели** (попытка 2, по умолчанию): причина провала —
  контекстная (критерии, вход, среда/инструмент), а не модель — модель не
  меняется, контекст уточняется причинами C12.
- **Смена модели без эскалации яруса**: модель-специфичный класс ошибки
  (нестабильный формат ответа, повторные отказы модели) — следующий
  кандидат того же яруса из fallback-цепочки.
- **Эскалация**: capability-причины провала — следующий ярус из
  fallback-цепочки; выше `modelHints.tier` более чем на один шаг за задачу
  — только режим complex или подтверждение пользователя. Альтернатива —
  смена сотрудника той же профессии (решение C06).
- Каждая эскалация — событие `model_escalated` с причиной (вердикт C12,
  класс ошибки). Без события эскалация запрещена.
- **Запрет платных внешних API при повторах**: ни повтор, ни смена модели,
  ни эскалация не рассматривают модели с `paidExternal: true` и не включают
  их в fallback-цепочки; автоматический переход на платные внешние API
  исключён. Использование платного API возможно только по явному разрешению
  пользователя на конкретную операцию и вне этого алгоритма.

## 5. Контроль расходов (совместно с C08 и C20)

Существующий Budget Manager уже предоставляет enforcement:

- допуск `startTask` с проверкой оценок и активных слотов;
- лимиты на задачу (стоимость/токены/длительность) — включаются политикой;
- месячные лимиты по агентам (`agentLimits`);
- блокировка при extra-платежах и abort активных задач;
- журнал usage с разрезами byAgent/byModel/byTask/byProject/bySession.

Специфика MAO добавляет:

- **Динамическая параллельность (этап 1.3)**: целевое число рабочих слотов
  (старт 2, до 20) вычисляет C20 и подаёт в политику C08 через единственный
  аддитивный канал; enforcement остаётся в C08; C11 только планирует
  (см. ADR-MAO-014: 20 слотов ≠ 20 одновременных вызовов — вызовы
  лимитируются политикой: бюджет, квоты подписки, лимиты адаптеров).
- **Категории расходов (ADR-MAO-012)**: money (реальные RUB — JSONL
  ledger), subscription (ChatGPT Plus: requestCount + приблизительный
  расход контекста; точные токенные квоты не постулируются), free
  (наблюдаемый usage бесплатных моделей), local (инструменты без LLM).
  Категория определяет, какой лимит расходует исполнение; двойной учёт
  исключён: классификация — проекция политики, ledger не вторая запись.
- **Бюджет ≤ 2 000 ₽/мес и его Budget Guard**: предстартовый gate (все
  категории), блокировка БЕЗ автоматических платных fallback/пополнений;
  подписка — фиксированный ежемесячный платёж, не API-баланс;
  подписочная авторизация Codex недоступна OpenCode.
- **Дневные предохранители**: предупреждение пользователю при
  warning/critical-статусе снимка (уже есть в C08) через UI.
- **Учёт успешности**: ModelStats обновляется из вердиктов C12 и usage;
  используется C05 (оценка планов) и C07 (ранжирование).
- **Кэшированные токены**: cacheRead/cacheWrite учитываются отдельно
  (поля уже есть в `RuntimeUsage` и `UsageEventInput`); отчёты C14
  показывают их долю для оценки эффективности продолжения сессий.

## 6. Метрики и отчётность

Для каждого исполнения фиксируются: input/output/reasoning/cacheRead/
cacheWrite/total, costUsd, длительность, runtimeReason, класс ошибки,
вердикт валидации. Агрегаты: помесячно, по модели, по профессии, по проекту;
success-rate и средняя стоимость успешной подзадачи — основные показатели
экономики офиса.

## 7. Fake Runtime и проверка без расходов

До подключения реальных моделей весь контур C05→C12 проверяется на fake-
реализации интерфейса `CoordinatorRuntime` (по образцу инжекции `spawn` в
тестах C15). Выбор модели при этом выполняется по-настоящему, а исполнение
имитируется с записью usage фиктивных метрик — так проверяются и лимиты
C08, и эскалации C07, и retry C06 без расхода квоты.

## 8. Связанные противоречия

- P-01 (запрет `modelId` в запросе координатора): разрешается введением
  C07 как единственного поставщика `modelId` для координатора; запрет на
  `modelId` от **пользователя** сохраняется. См. ADR-MAO-004.
