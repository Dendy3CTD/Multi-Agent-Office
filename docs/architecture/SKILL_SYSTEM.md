# MAO — SKILL SYSTEM

Система Skills: формат, реестр (C03), резолвер (C04). Размещение:
`packages/skills` (пустой → заполнить), данные — `skills/` в репозитории.

## 1. Цели

- 100–200+ узких Skills, включая общие для нескольких профессий.
- Загрузка в контекст модели **только необходимых** Skills (прогрессивное
  раскрытие); полный каталог никогда не передаётся в запрос.
- Добавление и изменение Skills без изменения ядра.

## 2. Стандартная структура Skill

Формат совместим с принятым в экосистеме форматом `SKILL.md`
(как в пользовательских skills), что позволяет переиспользовать готовые
материалы и инструменты.

```
skills/
├── shared/                       # общие Skills
│   └── markdown-report/
│       └── SKILL.md
├── coding/
│   └── code-review-checklist/
│       ├── SKILL.md
│       └── assets/…              # опционально: шаблоны, скрипты
└── cad/
    └── kompas-export/SKILL.md
```

`SKILL.md` — YAML-фронтматтер + Markdown-тело:

```yaml
---
id: code-review-checklist
version: 1.2.0
description: Проверка PR по чек-листу качества и безопасности
category: coding
tags: [review, quality, security]
requiredTools: [bash, read]
compatibleProfessions: [reviewer, developer]   # пусто = общий Skill
dependencies: [markdown-report@^1.0.0]
estimatedTokens: 900
status: active
---
# Тело: инструкции, чек-листы, шаблоны (русский язык,
# технические идентификаторы — без перевода)
```

Поля соответствуют `SkillDescriptor` (DATA_MODEL.md). Обязательные: id,
version, description, category. Остальные имеют значения по умолчанию.

## 3. Реестр (C03 Skill Registry)

- Обнаружение: сканирование `skills/**/SKILL.md` при старте и по команде
  reindex; динамическая регистрация через C16 (запись файла + индекс).
- Валидация: обязательные поля, формат id/semver, уникальность id, ссылки
  зависимостей существуют, `compatibleProfessions` ссылаются на активные
  профессии (предупреждение, не ошибка), `estimatedTokens` — положительное.
  Невалидный Skill отклоняется с событием `skill_rejected` и причиной;
  ядро не падает.
- Индекс в SQLite: id, версия, категория, теги, совместимость,
  estimatedTokens, путь к файлу. Тело в индекс не входит.
- Версии: одна активная версия на id (последняя валидная); история версий —
  через Git репозитория.

## 4. Резолвер (C04 Skill Resolver)

Вход: `SubtaskBrief` (теги, категория, риск), `ProfessionProfile`
(skillTags), дескрипторы C03, токен-бюджет контекста (от C09).

Алгоритм:

1. **Кандидаты по совместимости**: Skill общий ИЛИ professionId ∈
   compatibleProfessions; status=active.
2. **Ранжирование по релевантности**: пересечение тегов подзадачи с тегами
   Skill и skillTags профессии; обязательные Skills из `skillOverrides`
   сотрудника включаются всегда.
3. **Разрешение зависимостей**: топологическая сортировка, защита от
   циклов (цикл → отклонение с событием), диапазоны версий `^x.y.z`.
4. **Проверка инструментов**: `requiredTools` ⊆ инструментов среды
   исполнения проекта; недоступный инструмент → Skill отклоняется с причиной.
5. **Укладка в бюджет контекста**: сумма estimatedTokens ≤ лимит секции
   Skills (доля токен-бюджета C09); избыток отсекается по рангу.
   Стартовая норма: не более 5 Skills и ~4000 токенов на исполнение.

Выход: `SkillBundle` (упорядоченные `skillId@version`, тела для контекста,
список отклонённых с причинами). Событие `skills_resolved` фиксирует выбор.

## 5. Общие Skills

Skills без `compatibleProfessions` (или в `skills/shared/`) доступны любой
профессии. Примеры стартового набора: ведение отчёта Markdown, работа с
Git-историей, поиск по архиву, оформление кода, чек-лист безопасности.
Общие Skills проходят тот же резолв и бюджет контекста.

## 6. Взаимодействие с контекстом (C09)

- C09 вставляет тела Skills в секцию контекста между инструкциями профессии
  и постановкой подзадачи; порядок — топологический из C04.
- Ссылки на `assets/` Skill передаются путями; содержимое читается
  исполнением, а не включается в prompt.
- Событие `context_trimmed` при отсечении — с перечнем отсечённых Skills.

## 7. Стартовый набор и рост

- Существующие пустые каталоги `skills/roles/<role>/` сохраняются и
  заполняются профильными Skills при реализации; их текущее назначение
  (9 ролей) отражено в EMPLOYEE_SYSTEM.md.
- Начальные 30–40 профессий получают по 2–5 профильных Skills + общие —
  итого ~120–180 Skills без изменения механизмов.
- Добавление Skill: файл + `reindex` через C16. Удаление/отключение —
  `status: disabled`; резолвер исключает, история ссылок (skillBundle в
  подзадачах) остаётся читаемой по `skillId@version`.

## 8. Чего Skill не делает

- Не содержит секретов и не обращается к сети сам по себе (это делает
  исполнение через инструменты среды).
- Не выбирает модель и не меняет бюджет (только влияет через
  estimatedTokens на выбор C07/C09).
- Не исполняется ядром: Skill — инструкция для LLM-исполнения, а не код.
  Исполняемые хелперы в `assets/` запускаются только инструментами среды
  под контролем разрешений проекта.
