# MAO — EMPLOYEE SYSTEM

Профессии (C02), сотрудники (C01), их сессии (C10) и связь с визуальным
офисом. Размещение: `packages/directory` (новый пакет), данные —
`professions/` и SQLite.

## 1. Два уровня: Profession и Employee

**Profession** — декларативный профиль компетенций и ответственности
(файл `professions/<id>.md`, схема в DATA_MODEL.md). Не является процессом
и не потребляет ресурсов.

**Employee** — именованный экземпляр профессии в офисе: профиль,
инструкции, назначенная модель по умолчанию, индивидуальные Skills,
статус, визуальный персонаж. Тоже не процесс: «работает» только во время
исполнения подзадачи.

**Исполнение (Execution)** — кратковременный запуск Runtime-адаптера
(C15/C18 через C17, ADR-MAO-010), занимающий рабочий слот пула C11. Число
сотрудников (до 100+) не зависит от числа одновременных LLM-исполнений
(динамический пул: старт 2, цель до 20 рабочих слотов — ADR-MAO-014;
фактические LLM-вызовы лимитирует финансовая политика C08/C20).

## 1a. Отделы (Department)

Отдел — справочная группировка профессий (10–12 отделов, этап 1.3;
DATA_MODEL §2.1): выборка сотрудников, орг-отчёты, разделение зон
ответственности. Отдел **не является** процессом, бюджетом, слотом или
очередью; бюджетирование по проектам (C19), а не по отделам. Базовый
набор (уточняется): Руководство, Аналитика, Разработка, Инженерия/
CAD, Данные/ML, Медиа и дизайн, Архив/знания, Сопровождение/Операции,
Написание текстов, Юридическая поддержка. Каждая профессия принадлежит
ровно одному отделу (`ProfessionProfile.departmentId`).

## 3. Содержимое профиля профессии

Схема `Profession` — DATA_MODEL.md. Состав (пример для developer):

- ответственность и границы («не меняет схему БД без architect»);
- базовые инструкции (русский язык, по образцу существующего
  `apps/office/src/agentLanguage.ts` — он мигрирует в профили);
- skillTags → резолв Skills (C04);
- capabilityRequirements → фильтр моделей (C07);
- acceptancePolicy → политика приёмки (C12);
- modelHints → минимальный ярус (C07).

## 4. Независимость сотрудника

Каждый Employee имеет:

- собственные инструкции (профессия + переопределения);
- собственный набор Skills (`skillOverrides` поверх резолва);
- собственные сессии Runtime (C10; адаптер — OpenCode, Codex — по
  capabilities, ADR-MAO-010): одна активная сессия на сотрудника;
  сессия продолжается между его подзадачами в рамках проекта, если это
  дешевле (cacheRead) и не нарушает изоляцию задач. Сессия не привязывает
  сотрудника к модели или Runtime навсегда (ADR-MAO-011);
- собственную историю (события по employeeId в C14);
- собственный визуальный персонаж в офисе (при наличии спрайта).

## 5. Динамическая регистрация

- Новая профессия: файл `professions/<id>.md` → `POST /v1/professions`
  или reindex; валидация C02; событие `profession_registered`.
- Новый сотрудник: `POST /v1/employees` (professionId, имя, modelDefault…)
  или файл; валидация C01; событие `employee_registered`.
- Изменение: версия профиля увеличивается; активные задачи доисполняются на
  прежней версии (записанной в плане), новые — на новой.
- Отключение: `status: disabled`; новые назначения запрещены, активные
  подзадачи завершаются или отменяются по команде.

## 6. Ограничение параллельности и справедливость

- Пул рабочих слотов динамический: старт 2 LLM-исполнения, целевая ёмкость
  до 20 слотов; целевое значение вычисляет C20, enforcement — C08
  (`maxConcurrentTasks`). Слоты ≠ гарантированные одновременные LLM-вызовы:
  фактический вызовный лимит задаёт финансовая политика (ADR-MAO-012/014).
- Один сотрудник — максимум одно исполнение одновременно (защита сессии).
- Сотрудник не может проверять собственную работу: LLM-review выполняет
  другой сотрудник (C12).
- Director не дублируется: одна роль — один активный сотрудник профессии
  director (ограничение C01, снимаемое явной настройкой).
- При 100+ сотрудниках: реестр + пагинация API (C16), выбор исполнителя —
  по профессии и отделу; активность сотрудников ограничена ёмкостью пулов
  и приоритетами портфеля проектов (C19).

## 7. Связь с визуальным офисом

- Текущая сцена показывает 4 персонажей (Director, Developer, Engineer,
  Analyst) — сохраняется; Helper и новые сотрудники добавляются по мере
  появления спрайтов (Stage 9 ROADMAP, вне этапа 1.1).
- Отображение статусов: события шины → C16 → UI; соответствие
  employeeId ↔ visualCharacter хранится в профиле Employee.
- UI на этапе 1.1 не изменяется (ограничение задания).

## 8. Соответствие существующему коду и противоречия

- Сохраняется: таблица `DEFAULT_AGENT_MODELS` (как начальные данные C01),
  запрет автозапуска Helper, правило заменяемости моделей через
  конфигурацию (принцип 5 AGENTS.md).
- P-04: жёстко заданные пять агентов координатора заменяются реестром;
  `normalizeAgentModels` остаётся валидатором формата id при инициализации.
- Несоответствие названий: существующие пустые каталоги `skills/roles/`
  (analyst, coder, designer, director, engineer, lawyer, modeller, reviewer,
  tester) не совпадают с целевым списком профессий (например, `lawyer`,
  `coder`, `modeller` в нём отсутствуют как id). Решение: каталоги
  считаются заготовками; канонические id — из `professions/`; соответствие
  устанавливается при наполнении, лишние каталоги архивируются решением
  пользователя.
