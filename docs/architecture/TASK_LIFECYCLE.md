# MAO — TASK LIFECYCLE

Жизненный цикл задачи от поступления до архива. Компоненты и сущности —
по COMPONENTS.md и DATA_MODEL.md.

## 1. Статусы Task

`received → analyzing → planned → running → validating → accepting →
completed | failed | cancelled` (+ `recovery` после перезапуска).

Статусы Subtask: `queued → running → validating → done | failed | cancelled`
(+ `retrying` как подсостояние queued с увеличенным `attempts`).

Каждый переход — событие в шину C06 (фиксируется C14 до отображения в UI).

## 2. Основной сценарий (standard/complex)

### Шаг 1. Приём и анализ (C16 → C05)

1. Пользователь отправляет задачу через Server API (`POST /v1/tasks`).
2. C05 нормализует запрос, классифицирует сложность правилами:
   - **simple** — одна профессия, один исполнитель, без декомпозиции;
   - **standard** — 2–4 подзадачи;
   - **complex** — глубокая декомпозиция, обязательная приёмка Director.
   LLM не привлекается для simple/standard (принцип экономии).

### Шаг 2. Планирование (C05)

3. Определяются необходимые профессии (по тегам/правилам; для complex —
   опционально Director-LLM как отдельное бюджетное исполнение).
4. Задача разбивается на подзадачи; строится DAG зависимостей; каждой
   подзадаче назначаются критерии приёмки.
5. Назначаются сотрудники (C01): профессия → активный сотрудник; если
   свободных нет — сотрудник назначается последовательно (сотрудники не
   равны слотам LLM, см. EMPLOYEE_SYSTEM.md).
6. C04 резолвит SkillBundle для каждой подзадачи (профессия + теги).
7. C07 даёт предварительную оценку стоимости плана (дешёвые модели по
   умолчанию). Если оценка превышает лимиты C08 — задача возвращается
   пользователю с объяснением до расхода токенов.

### Шаг 3. Запуск (C06 → C11 → C08)

8. C06 ставит готовые подзадачи (без незакрытых зависимостей) в очередь C11.
9. C11 выдаёт слоты пула: динамическая ёмкость (старт 2 LLM-исполнения,
   цель до 20 рабочих слотов — ADR-MAO-014). Фактический допуск —
   `BudgetManager.startTask` через существующий координатор (Budget Guard
   с этапа 2: ADR-MAO-012); превышение лимита политики невозможно
   архитектурно.
10. Для подзадачи C07 выбирает модель и Runtime (Model Gateway, дешёвая
    подходящая; MODEL_ROUTING.md), C09 собирает минимальный контекст,
    C10 открывает или продолжает сессию сотрудника, координатор запускает
    Runtime-адаптер (сейчас — C15; этап 2 — через C17).

### Шаг 4. Исполнение (C15 через координатор)

11. События Runtime текут в шину (UI наблюдает в реальном времени), usage
    фиксируется в C08 (уже реализовано: `onUsage` → `recordUsage`).
12. Превышение лимитов/таймаута/отмены — типизированные ошибки C15;
    координатор гасит процесс; C06 переводит подзадачу в retry или failed
    по политике.

### Шаг 5. Передача результатов (C13)

13. Артефакты регистрируются с манифестом (путь, хэш, размер). Зависимым
    подзадачам C09 передаёт ссылки и выдержки — не полные содержимые.

### Шаг 6. Автоматическая проверка (C12)

14. Выполняются критерии приёмки подзадачи: сначала детерминированные
    проверки (тесты, линтеры, наличие файлов, схемы) — без расхода токенов.
15. Если `acceptancePolicy` требует review — независимая LLM-проверка
    сотрудником reviewer-профессии (отдельное бюджетное исполнение через
    обычный путь, со своей дешёвой моделью от C07).
16. Вердикт: `pass` → подзадача `done`; `partial/fail` → рекомендация
    retry/escalate/replan.

### Шаг 7. Повторные попытки (C06 + C07)

17. Политика retry (по умолчанию): до 2 повторов на подзадачу.
    - Попытка 2: та же модель, уточнённый контекст (причины провала от C12).
    - Попытка 3: эскалация модели на ярус выше (C07, с записанным
      обоснованием), либо смена сотрудника той же профессии.
    - Исчерпание попыток: подзадача `failed`; C06 либо перепланирует ветку
      (`plan_revised`), либо переводит задачу в `failed` с отчётом.

### Шаг 8. Финальная приёмка

18. Все подзадачи `done` → задача `accepting`.
    - **auto** (simple/standard): детерминированная сверка критериев
      верхнего уровня — C12.
    - **director** (complex): Director-профиль получает сводку результатов
      и вердикты через обычное исполнение и выносит решение. Это единственное
      обязательное LLM-участие Director; в simple/standard Director не
      используется.
19. Задача `completed`; `resultSummary` формируется из итогов подзадач
    (правилами; LLM-суммаризация — только по запросу пользователя).

### Шаг 9. Архивирование (C14)

20. События уже durable в SQLite; экспортёр переводит их через outbox в
    Markdown-архив Obsidian (проект, задача, подзадачи, решения, отчёт
    валидации, usage, ссылки на артефакты). UI показывает архивные ссылки.

## 3. Fast path (simple)

```
C16 → C05 (classify=simple) → назначение 1 сотрудника → C04 (минимум Skills)
→ C07 (самая дешёвая подходящая модель) → слот C11 → исполнение → C12
(только детерминированные проверки) → done → C14
```

Ограничения fast path: одна подзадача, один исполнитель, одно исполнение,
без декомпозиции, без Director, без LLM-review (кроме явной
`acceptancePolicy` профессии). Большинство бытовых запросов офиса должны
идти именно этим путём.

## 4. Отмена и восстановление

- Отмена пользователем: `POST /v1/tasks/:id/cancel` → C06 вызывает
  `cancelTask` координатора (AbortSignal → SIGTERM → SIGKILL, уже
  реализовано), статусы `cancelled`, события зафиксированы.
- Отмена бюджетом: `BudgetExceededError` по сигналу — задача `failed` с
  причиной `budget`; новые исполнения блокируются до решения пользователя.
- Перезапуск процесса: при старте C06 читает SQLite; `running`/`validating`
  → `recovery`; решение — retry с новой попытки (usage прошлых попыток уже
  в ledger и учитывается лимитами).

## 5. Гарантии экономии

- LLM вызывается только на шагах 10, 15 (опционально), 18 (только complex)
  и опционально на шаге 3 для complex-планирования.
- Все проверки, выполнимые инструментами, выполняются инструментами (шаг 14).
- Контекст каждого исполнения ограничен (C09), история диалога целиком не
  передаётся.
- Превышение лимита параллельности невозможно ни при какой ошибке
  планировщика: enforcement — в C08 (`maxConcurrentTasks` — динамическое
  значение политики от C20), а не в C11. 20 рабочих слотов ≠ 20
  одновременных LLM-вызовов: вызовы ограничены финансовой политикой
  (ADR-MAO-012/014).
