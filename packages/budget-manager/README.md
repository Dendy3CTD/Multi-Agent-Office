# Budget Manager

Независимый модуль учёта usage OpenCode и применения локальной бюджетной
политики. Пакет не выполняет сетевых запросов, не покупает кредиты, не знает
остаток allowance OpenCode Go и не подключается к Runtime автоматически.

`usage.costUsd` хранится отдельно от фактических платежей в RUB. USD не
конвертируется в RUB без явно заданного курса.

Политика по умолчанию: подписка OpenCode Go оплачена и стоит 1000 ₽
(`subscriptionCostRub = 1000`), месячный денежный лимит 1000 ₽
(`monthlyBudgetRub = 1000`), поэтому дополнительный денежный бюджет равен 0 ₽.
Дополнительные платные расходы запрещены (`extraUsageEnabled = false`).
Запросы внутри включённой квоты OpenCode Go разрешены: подписка не является
дополнительным расходом и не блокирует задачи. Allowance Go всегда имеет статус
`unknown`, потому что Runtime не предоставляет достоверный остаток квоты.
Это локальная политика приложения. Она не подтверждает, что дополнительные
платные запросы отключены в настройках аккаунта OpenCode.

## Календарный месяц

Все месячные расчёты используют период `[from, to)`: `from` — первый момент
текущего месяца, `to` — первый момент следующего, в часовом поясе
`accountingTimeZone` (по умолчанию `UTC`, IANA-имя, например `Europe/Moscow`).

- Платежи и usage хранятся вечно; в текущий месячный бюджет попадают только
  записи текущего периода. Исторические записи не удаляются.
- Подписка (`subscriptionCostRub`) считается месячным расходом текущего периода.
- `extraSpendRub`, `actualSpendRub`, `monthlyUsage` и месячные лимиты сотрудника
  (`agentLimits`) отражают только текущий период.
- Платёж прошлого месяца не блокирует новый месяц.

Статус cash-budget вычисляется только по дополнительным RUB-платежам текущего
месяца (`recordCashPayment`) относительно дополнительного бюджета
(`extraBudgetRub = monthlyBudgetRub - subscriptionCostRub`): `normal`,
`warning` от 70%, `critical` от 90%, `blocked` при 100% и больше. При нулевом
дополнительном бюджете любой платёж текущего месяца переводит статус в
`blocked`, и новые задачи (включая квотные) не стартуют, пока месяц не сменится.
Квотные задачи разрешены при отсутствии такого дополнительного расхода.
Если `subscriptionCostRub = null`, статус `unknown`.

## Платежи: постоянное хранение

`recordCashPayment()` и `getCashPayments()` асинхронные. Платежи сохраняются
через `CashPaymentStore`; стандартная реализация — `JsonlCashPaymentStore`
(встроенный `node:fs`, путь должен быть абсолютным).

```ts
const manager = new BudgetManager(
  new JsonlUsageStore("/absolute/path/usage.jsonl"),
  {
    paymentStore: new JsonlCashPaymentStore("/absolute/path/cash-payments.jsonl"),
  },
);
await manager.recordCashPayment({ paymentId: "pay-2026-11-01", amountRub: 250, timestamp: "2026-11-01T09:00:00.000Z" });
```

- В файл пишутся только `paymentId`, `amountRub`, `timestamp`. Поля вроде
  `description`, prompts, ответы, токены и пароли не сохраняются.
- Повторная запись идентичного платежа (тот же ID, сумма и время) не создаёт
  новой строки и не увеличивает расходы.
- Тот же `paymentId` с другими данными отклоняется `CashPaymentConflictError`,
  журнал не меняется.
- При загрузке повреждённые, неполные и невалидные строки пропускаются.
  Если в журнале есть два конфликтующих платежа с одним ID, загрузка падает с
  `CashPaymentConflictError`: модуль не выбирает одну из двух записей молча.
- Если строка оборвалась без перевода строки (сбой записи), следующая запись
  начинается с новой строки.
- Записи в одном процессе сериализуются очередью. Межпроцессной блокировки нет.
- Без `paymentStore` операции с платежами, `getSnapshot()`, `checkTaskStart()`
  и `startTask()` завершаются `BudgetStoreError` ("not configured"). Учёт usage
  при этом продолжает работать.

Загрузка журналов выполняется при первом обращении (или явным `load()`), потому
что конструктор синхронный. Экземпляр не перечитывает журнал платежей, если
другой экземпляр в том же процессе записал платёж после его загрузки.

## Единая очередь операций

`startTask()`, `recordCashPayment()` и `recordUsage()` выполняются в одной
in-process FIFO-очереди. Проверка лимитов, регистрация задачи и запись usage или
платежа не могут пересекаться внутри процесса. Вложенных блокировок нет, поэтому
взаимного ожидания (deadlock) быть не может. `checkTaskStart()` и чтение
снимков очередь не используют. Межпроцессной гарантии нет.

- `startTask()` — единственная операция, которая резервирует слот.
- `checkTaskStart()` — только предварительная проверка без регистрации.

```ts
const task = await manager.startTask({ taskId: "task-1", agentId: "developer", estimatedCostUsd: 0.05 });
try {
  await manager.recordUsage({
    eventId: "usage-1",
    agentId: "developer",
    modelId: "opencode-go/claude-haiku-5-5",
    taskId: "task-1",
    input: 100,
    output: 50,
    reasoning: 10,
    cacheRead: 0,
    cacheWrite: 0,
    total: 160,
    costUsd: 0.01,
  });
} finally {
  task.release();
}
```

`release()` обязателен: он освобождает слот и очищает таймер. Он идемпотентен.

## Остановка задач при дополнительном денежном расходе

Если `recordCashPayment()` записал платёж текущего месяца и бюджет стал
`blocked`, все активные задачи получают `abortController.abort(BudgetExceededError)`
с причиной «extra RUB spend recorded for the current month: extra budget
exhausted». Задачи остаются в `activeTasks`, пока Runtime не завершит процесс и
не вызовет `release()`. Модуль сам процессы не останавливает.

- Платёж прошлого месяца задачи не останавливает.
- Повторная идентичная запись платежа не имеет побочных эффектов: ни повторного
  `abort()`, ни новой строки в журнале.
- Конфликтующий платёж отклоняется и задачи не трогает.

## Ограничение длительности задачи

Если задан `maxTaskDurationMs`, таймер взводится на **оставшееся** время:
`maxTaskDurationMs - (now - startedAt)`, где `now` — инъецируемые часы. Задержка
между `startedAt` и регистрацией задачи расходует лимит и не продлевает его.

- Если лимит уже достигнут, `startTask()` отклоняет задачу
  (`BudgetExceededError`), таймер не взводится. `checkTaskStart()` возвращает
  `allowed: false`.
- `startedAt` в будущем отклоняется, иначе лимит можно было бы растянуть.
- При срабатывании вызывается `abortController.abort(BudgetExceededError)`.
  Слот остаётся занятым до `release()`. Таймер `unref`, поэтому не удерживает процесс.
- `release()` очищает таймер. Старый таймер не может отменить новую задачу с тем же
  `taskId`: срабатывание сверяет ссылку на запись, а не только ID.
- Значение не может превышать 2^31-1 мс, потому что `setTimeout` не поддерживает
  большие задержки.
- Таймер использует системное время процесса, а инъецируемые часы задают только
  оставшееся время на момент старта и проверки usage events.

Длительность также проверяется на каждом usage event по инъецируемым часам. Если
usage приходит уже после лимита, он записывается, а `recordUsage()` выбрасывает
`BudgetExceededError`. Таймер и usage-проверка идемпотентны.

## Журнал usage

`JsonlUsageStore` записывает одну запись `UsageRecord` на строку.

- Запись идёт через `FileHandle`. Если предыдущая запись оборвана без LF, новая
  начинается с новой строки, поэтому записи не склеиваются.
- После каждой записи выполняется `handle.sync()` (fsync). При создании
  файла также делается fsync каталога, где это поддерживается.
- Каталог создаётся с правами 0700, журнал — с 0600. Существующий журнал получает
  0600 при записи (best effort: если `chmod` не удался, права не меняются).
  Существующий каталог не переназначается.
- В файл попадают только поля `UsageRecord`. Лишние поля (prompts, ключи) отбрасываются.
- При чтении каждая строка проверяется: идентификаторы, ISO-дата с часовым поясом,
  конечные неотрицательные метрики, отсутствие лишних полей. Невалидные и
  повреждённые строки пропускаются.
- Одинаковый `eventId` с одинаковыми данными — no-op (`false`). С другими данными —
  `UsageEventConflictError`, журнал не меняется. Два конфликтующих события в файле
  приводят к ошибке загрузки.
- Записи в одном процессе сериализуются. Межпроцессной блокировки нет.

## Usage и лимиты

Промежуточные usage events проверяются на границах записи/`step_finish`.
Уже выполняющийся шаг может дать перерасход до момента следующего события;
модуль не обещает абсолютного предотвращения превышения, если провайдер не даёт
предварительный token cap.

Лимиты сотрудника (`agentLimits`) — месячные: учитывается usage сотрудника за
текущий календарный период. Проверка при старте задачи использует
`текущее использование + оценка`.

## Валидация

Отклоняются с `TypeError`: NaN, Infinity и отрицательные значения в usage,
оценках задачи и суммах платежей; невалидные `taskId`, `agentId`, `paymentId`,
`eventId`, `projectId`, `sessionId` (1-128 символов: буквы, цифры, `.`, `_`, `:`, `-`,
первый символ буквенно-цифровой); даты, которые не являются ISO 8601 date-time с
часовым поясом (`Z` или `+hh:mm`), в `startedAt`, `timestamp`. Некорректное число
не может обойти лимит сравнением с NaN.

## Ограничения

- Модуль не подключён к Runtime, orchestrator, server и office.
- Синхронизация и дедупликация работают только внутри одного процесса.
- Модуль учитывает только внесённые вручную RUB-платежи. Списания, о которых не
  сообщено, он не обнаруживает.
- Остаток квоты OpenCode Go неизвестен (`allowanceStatus: unknown`).
- Лимиты per-task считаются по всей истории `taskId` в журнале usage.
